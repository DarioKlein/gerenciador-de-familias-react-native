## Product purpose and constraints

- Product name: `GerenciamentoDeFamiliasMobile`.
- The app replaces the user's father's Excel workbook with a simple Android-first mobile app for registering and consulting families.
- The primary user is one non-technical person. Optimize for large readable text, high contrast, large touch targets, clear labels, few taps, and simple screens.
- The app must work offline. Family data is stored only on the device in SQLite.
- There is no login, server, cloud synchronization, multi-device synchronization, or role-based access in v1.
- The v1 supports a dashboard, family list, search and filters, family details, create/edit/delete, map links, XLSX export/import, and a one-time importer for the legacy `SETOR_7.xlsx` workbook.
- Deletion always requires confirmation. Import always requires a preview. Never show `null` or `undefined` in the UI.
- Google Maps and Waze require internet, but all other core family-management flows must work in airplane mode.

## Approved navigation model

Use Expo Router with a root stack and three bottom tabs:

```text
Início (dashboard)
Famílias (list, search, filters)
  -> Family details
  -> Create family
  -> Edit family
Backup (export/import)
```

- Show a prominent `+ Nova família` action on the dashboard and family list.
- Reuse the same form implementation for create and edit modes.
- Returning from details or forms should preserve list search and filters.
- Route files and `_layout.tsx` files belong in `src/app/`. Keep database, repositories, domain types, validation, hooks, utilities, and reusable components outside `src/app/`.

## Approved family data model

SQLite table `familias`:

| Column | SQLite type | Required | Notes |
| --- | --- | --- | --- |
| `id` | TEXT | yes | Stable UUID generated by the app; primary key; exported to XLSX. |
| `nome` | TEXT | yes | Family or responsible person's name. |
| `endereco` | TEXT | yes | Street or avenue without the house number. |
| `cep` | TEXT | no | Brazilian postal code formatted as `00000-000`; address lookup is optional and requires internet unless cached. |
| `numero` | TEXT | no | Text to support values such as `S/N`, `45-A`, and `FUNDO`. |
| `bairro` | TEXT | no | Suggest existing neighborhoods to reduce spelling variants. |
| `cidade` | TEXT | no | Legacy column name used for the fixed locality/district selection. |
| `telefone` | TEXT | no | Keep as text to preserve prefixes, punctuation, and leading zeroes. |
| `numero_moradores` | INTEGER | no | Optional non-negative integer for total household residents. |
| `numero_criancas` | INTEGER | no | Optional non-negative integer for children in the household. |
| `numero_idosos` | INTEGER | no | Optional non-negative integer for elderly residents. |
| `numero_enfermos` | INTEGER | no | Optional non-negative integer for sick/ill residents. |
| `numero_batizados` | INTEGER | no | Optional non-negative integer for baptized residents. |
| `cargo` | TEXT | no | Legacy single-role column retained for migration compatibility; new writes use `familia_cargos`. |
| `ministerio` | TEXT | no | At most one value from the fixed ministry list. Independent from cargos. |
| `situacao_religiosa` | TEXT | no | A single value from the religious-status list. It is not multi-select. |
| `situacao_economica` | TEXT | no | A single value from the economic-status list. |
| `residencia` | TEXT | no | `Própria` or `Alugada`. |
| `ultima_visita` | TEXT | no | Optional `YYYY-MM-DD` date of the last registered family visit. |
| `criado_em` | TEXT | yes | ISO 8601 timestamp generated automatically. |
| `atualizado_em` | TEXT | yes | ISO 8601 timestamp refreshed on each edit. |

- Do not add an `observacao` field.
- Religious status and economic status are separate concepts and separate fields.
- Religious status is single-choice and mutually exclusive. Allowed values: `Congrega`, `Parado`.
- Economic status values: `Aposentado`, `Desempregado`, `Registrado`, `Encostado`, `Autônomo`.
- Locality values stored in the legacy `cidade` column: `Cândido Mota` (municipal seat), `Alexandria`, `Porto Almeida`, `Frutal do Campo`, `Guaripu` (districts).
- Show this field as `Localidade / distrito`; never imply that the districts are separate municipalities.
- CEP queries use the official municipality and state `Cândido Mota/SP`. They may fill street and neighborhood, but must not overwrite the selected locality/district without confirmation.
- Keep CEP lookup optional. When offline or the service is unavailable, preserve manual address entry and use cached successful queries when possible.
- Role values: `Auxiliar de jovens`, `Administração`, `Porteiro(a)`, `Músico`, `Organista`, `Auxiliar do som`.
- Ministry values: `Cooperador de jovens`, `Cooperador oficial`, `Diácono`, `Ancião`, `Encarregado de orquestra`, `Irmã da obra da piedade`.
- Residence values: `Própria`, `Alugada`.
- Legacy records without a religious status remain null and are displayed as `Não informado`.
- Legacy `CONTATO` entries in the old workbook are not phone numbers; the new `telefone` field remains empty unless a real number is available.
- Use TypeScript literal unions derived from `as const` arrays for fixed lists. Do not rely on unrestricted strings in application/domain code.
- Enforce fixed values with SQLite `CHECK` constraints as well as TypeScript and form validation.
- A family/person can have zero, one, or multiple cargos simultaneously. Store them in `familia_cargos`, keyed by `(familia_id, cargo)`.
- Ministry remains optional and single-choice. Cargos and ministry are independent and may coexist.
- Backfill values from the legacy `familias.cargo` column into `familia_cargos`, then clear the legacy column so the old exclusivity constraint cannot block a ministry; do not use that column for new writes.
- Store UUIDs, phone numbers, house numbers, and ISO 8601 timestamps as SQLite `TEXT`. Convert timestamps to `Date` only when date operations are needed.
- Use parameterized SQL for every value. Never build SQL by concatenating user input.
- Add indexes for fields used by list/search/filter queries, initially `nome`, `bairro`, `cidade`, and `cep`.
- Use a small versioned initialization/migration runner based on `PRAGMA user_version`, even for the first schema. Never run destructive migrations without explicit approval.

## Search, maps, import, and export rules

- Search must ignore case and accents. Because the expected data set is small (about 66 families initially), correctness and clarity are more important than premature database optimization.
- Build map search text from non-empty parts of `endereco`, `numero`, `bairro`, `cidade`, followed by `SP, Brasil`.
- Encode map query text with `encodeURIComponent` and open Google Maps or Waze through React Native `Linking`.
- Disable map actions with `Endereço incompleto` when there is not enough address data. Test both map links on a real Android device before considering the feature complete.
- Standard export format is `.xlsx`, sheet `Familias`, one row per family, with a second `LEIAME` sheet describing columns and allowed values.
- Use `id` as the stable import/update key. Importing a previously exported file must not duplicate families.
- Invalid import rows are not persisted and must show a clear reason in the preview.
- The legacy workbook importer ignores population-count columns and footer contact blocks. Missing legacy religious status remains null.
- Exported Excel files are the real backup against app uninstall or Android data deletion; internal copies do not survive those actions.

## Technical direction and implementation order

- Use direct SQL through `expo-sqlite`; do not add an ORM for v1.
- Generate stable IDs with `expo-crypto` UUID generation.
- Later spreadsheet/file features should use SDK-compatible packages installed through `npx expo install` where applicable, and the selected XLSX library only after explicit user approval.
- Implement in vertical slices:
  1. SQLite initialization and schema.
  2. Family domain types, constants, validation, and repository.
  3. Family list and create flow.
  4. Details, edit, and confirmed deletion.
  5. Dashboard, search, and filters.
  6. Google Maps and Waze links.
  7. XLSX export/import and backups.
  8. One-time legacy `SETOR_7.xlsx` importer.
- The first usable milestone is complete only when a family can be created, listed, viewed, edited, deleted with confirmation, and remains present after restarting the app.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md
